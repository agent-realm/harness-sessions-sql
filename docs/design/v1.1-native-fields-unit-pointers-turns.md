# Proposal for v1.1: native fields, unit pointers and a turns view

**Status: proposal.** Nothing here is part of the specification until it is accepted, and it
becomes normative only once an implementation or a fixture test backs it (AGENTS.md rule 2). Every
addition is optional and additive, so it fits a v1.x under rule 5.

## The problem

harness-sessions-sql keeps a session in two layers. `session_units` holds each harness's native
records, byte for byte. The entity tables (`sessions`, `session_parts`, `session_usage`,
`session_links`, `session_lifecycle`) hold the fields every harness shares, as columns. A query
across harnesses reads the columns, and a query about one harness can filter on `harness`.

Two things are missing for a query about one harness:

1. **The fields no column maps.** A harness keeps more than the shared shape: a Claude Code
   `gitBranch`, a Codex `sandbox_policy`, a Zed `profile`. Today the only way to reach them is to
   find the raw unit and parse it again.
2. **The way back to the raw unit.** An entity row does not say which units it was derived from.
   `session_parts` has the session key and the message and part ids, but no `source_key` or
   `unit_key`, so a reader cannot join a part to its unit without re-running the adapter.

A third gap is a common question with no answer in the tables: **what happened in one turn**, from
a person's prompt to the next one.

## What this proposes

Three additions, each usable without the others.

| # | Addition | Where | Needs a sessions-model change |
|---|---|---|---|
| A | `native`: the record's native fields that no other field carries | sessions-model record field; columns on `sessions` and `session_parts` | yes, an optional field (v1.x) |
| B | `units`: the raw units a record was derived from | sessions-model record field; columns on `sessions` and `session_parts` | yes, an optional field (v1.x) |
| C | `session_turns`: one row per turn | a view over `session_parts` | no |

The order across repositories follows the dependency rule (AGENTS.md): sessions-model first, then
the adapters, then this mapping, then the stores.

### A. `native`

**In sessions-model** (an additive optional field, as §8 of that contract allows in a v1.x):
- `native` on `session` and `message` records, and on each part: an object holding the fields of
  the native record that the record's other fields do not carry. The adapter decides what it holds,
  per harness, and redacts it like every other field (sessions-model §4). It has no meaning across
  harnesses.
- Absent when the adapter emits none. `{}` when it emits it and nothing was left over.
- It is part of the record, so it is inside `content_sha`. It is outside `cmp_sha`, whose
  projection names its fields.

**In this mapping:**
- `sessions.native`, and `session_parts.message_native` and `session_parts.part_native`. A message
  field is repeated on each of its part rows, as the other message fields are.
- **The canonical JSON text, never a JSON-typed column.** ClickHouse: `String`, holding the JCS
  (RFC 8785) text of the object, `''` when absent, as `setup` and `args` hold theirs. PostgreSQL:
  `jsonb`, null when absent.
- Out of every key. Redaction holds (§8) applies unchanged: the column holds only what the record
  holds.

**Why not ClickHouse's `JSON` type.** It was measured on ClickHouse 26.8 and 26.10, against the 12
adapters' synthetic fixtures (harness-session-adapters 1.0.0: 1659 raw units, 1258 records):
- **It is a parser, not a store.**
  - 109 of the 1659 units are refused, because they are not JSON objects: YAML, plain text,
    base64, and a unit that is wholly a redaction marker.
  - Of the rest, 304 come back byte-identical on default settings, and 585 with every setting that
    helps. Keys come back sorted and number lexemes rewritten.
  - `null` and `{}` are dropped, a key with a dot becomes a nested object, and an integer beyond
    64 bits becomes a string.
- **Its text depends on the reader.** An ISO timestamp becomes `DateTime64` with its zone
  dropped. The text read back then depends on the reader's `session_timezone`, and on the other
  rows in the same insert. One stored row gave three different sha256 under three reader settings.
- **One path can hold several types.** In the fixtures, 21 paths hold more than one type, 7 of
  them across harnesses. `j.id = 1` is an error where `id` is a string in one harness and an
  integer in another.
- **Cost.**
  - One question across harnesses over 1M rows took 13 ms on typed columns, 240 ms on JSON paths
    and 780 ms on `String` with `JSONExtract`.
  - The `JSON` column was 3 to 3.4 times the size of the same text under ZSTD(3).
  - On 26.8, merging it at 1M rows needed more than 5.4 GiB.

The canonical text is exact and hashable. Reading it costs `JSONExtract` time, and that cost falls
only on queries about one harness, because the shared fields are already columns. A deployment
that wants faster paths may add a derived, typed column for one path (docs/guides,
add-a-column-without-breaking-conformance), as it may for any derived value.

### B. `units`

**In sessions-model** (an additive optional field):
- `units` on every record: the units the record was derived from, as
  `[source_key, generation, unit_key]` triples, sorted.
- **Outside `content_sha`.** A stream that is rewritten gets a new generation and new unit keys
  while its records stay the same. Inside the hash, every such reset would revise every record.
  Outside it, a record keeps the triples from its last revision. They still name units that
  produced its content, because `session_units` is append-only.
- Excluding a field from `content_sha` changes no existing hash, because no record carries
  `units` today.

**In this mapping:**
- `sessions.units`, and `session_parts.message_units`, repeated on each part row. ClickHouse:
  `Array(Tuple(source_key String, generation UInt32, unit_key String))`. PostgreSQL: `jsonb`, an
  array of triples.
- A reader joins them to `session_units` on the session key plus the triple (a unit of several
  chunks has one row per chunk).

### C. `session_turns`

A turn starts at a message a person sent (`role = 'user'`, `source = 'user'`) and runs to the next
such message. Messages before the first prompt are turn 0. Only the current state counts
(`is_deleted = 0`, `removed = 0`, §6). The message and the part must be current, and on the
active branch where the harness store keeps branches.

ClickHouse:

```sql
CREATE VIEW session_turns AS
WITH
  parts AS (
    SELECT * FROM session_parts FINAL
    WHERE is_deleted = 0 AND removed = 0
      AND state = 'current' AND part_state IN ('', 'current')
      AND ifNull(on_active_branch, true)
  ),
  messages AS (
    SELECT host, harness, harness_path, session_id, incarnation, message_id,
           any(order_key) AS order_key,
           toUInt32(any(role) = 'user' AND any(source) = 'user') AS is_prompt
    FROM parts
    GROUP BY host, harness, harness_path, session_id, incarnation, message_id
  ),
  numbered AS (
    SELECT *, sum(is_prompt) OVER (
             PARTITION BY host, harness, harness_path, session_id, incarnation
             ORDER BY order_key, message_id
             ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS turn
    FROM messages
  )
SELECT p.host, p.harness, p.harness_path, p.session_id, p.incarnation, n.turn,
       anyIf(p.message_id, n.is_prompt = 1)          AS prompt_message_id,
       min(p.ts)                                     AS started_at,
       max(p.ts)                                     AS ended_at,
       uniqExact(p.message_id)                       AS messages,
       countIf(p.kind = 'tool_call')                 AS tool_calls,
       countIf(p.kind = 'tool_result' AND p.is_error) AS tool_errors,
       groupUniqArrayIf(p.served_model, p.served_model != '') AS served_models
FROM parts AS p
INNER JOIN numbered AS n USING (host, harness, harness_path, session_id, incarnation, message_id)
GROUP BY p.host, p.harness, p.harness_path, p.session_id, p.incarnation, n.turn;
```

This SQL is a draft and has not been run yet. Before acceptance, an example (06) runs it against
both database profiles.

PostgreSQL takes the same shape: `DISTINCT ON` or `GROUP BY` for `messages`, the window `sum`
for `turn`, and `bool_or` and `array_agg(DISTINCT …)` in the outer query.

`ts` is null for harnesses whose store keeps no time (`ts_source = 'none'`), so `started_at` and
`ended_at` are null there. Usage per turn is left out: `session_usage` anchors usage on a response, a message, the session or
a compaction (sessions-model §2.4), at several granularities, `per_turn` among them. A join that
counts each usage once per turn is a question of its own (below).

## What it costs

- **sessions-model v1.x:** two optional fields, `native` and `units`, and the `content_sha`
  exclusion for `units`.
- **The adapters:** each adapter emits them, behind an `adapter_ver` bump, because its records
  change. A consumer re-derives from its archive, as on any such bump.
- **This mapping:** five columns (§4.2, §4.3) and one view (§6), marked (plan) until backed. The
  conformance kit gains two checks:
  - every `units` triple names a unit in `session_units`;
  - `native` passes Redaction holds, which needs no new code.
  An example 06 would show a turn and a native field read through `units`.
- **Stores:** memhouse, the first production implementation, adds the columns and the view, and
  keeps its archive as it is.

## Open questions

1. **What `native` holds.** "The fields the record's other fields do not carry" leaves the adapter
   to decide. For a message folded from several native lines (Claude Code), is `native` per line
   or merged? This proposal says merged into one object, keyed by the native field names, with
   the adapter's choice documented in its `describe()`.
2. **`native` on `usage`, `link` and `lifecycle`.** This proposal leaves them out. Add them later,
   if a query needs them.
3. **`units` and the `removed` vanish policy.** Under `"policy": "removed"` the units go, and a
   record's triples point at nothing. Should the engine clear `units`, or is a dangling pointer
   acceptable for a removed source?
4. **`units` outside `content_sha`.** An engine that writes a new `rev` only when `content_sha`
   moves keeps stale triples after a reset. They are still valid, but they name an older
   generation. Is that acceptable, or should `units` be inside the hash and the churn accepted?
5. **Usage per turn.** Which anchor wins when a usage record is anchored on a response that spans
   two turns?
6. **The turn boundary.** Should `source = 'steering'` (a message sent mid-turn) or
   `source = 'automated'` (a loop or a schedule) also start a turn? This proposal starts one only
   for `user`.
